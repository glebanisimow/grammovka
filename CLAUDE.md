# Граммовка: Android-приложение для учёта калорий

Ты ведёшь разработку нативного Android-приложения от нуля до рабочего APK. Этот файл — твоя постоянная инструкция: архитектура, инварианты, фазы и правила работы. Если что-то здесь противоречит просьбе пользователя в сессии, спроси, что из этого актуально, и обнови файл.

## Контекст и цель

- Один пользователь, Android-телефон, живёт в Польше: упакованные продукты в основном польские.
- Задача: держать заданный темп снижения веса, а цель по калориям пересчитывать по фактическому расходу, восстановленному из записей и тренда веса. Калории с часов и фитнес-трекеров в бюджет не входят никогда.
- Главная метрика продукта — трение при записи. Повторный продукт записывается за 2–3 тапа, новый — один раз с подтверждением, дальше он берётся из локального каталога.
- Распространение: подписанный APK без Google Play. Каждый push в `main` → GitHub Actions собирает и подписывает release-APK и публикует его в релиз `android` публичного репозитория (`update.json` + APK). Первая установка — `grammovka-latest.apk` из релиза, дальше «Настройки → Обновление» в приложении. Ручных шагов нет.
- Интерфейс на русском. Код, идентификаторы, комментарии и коммиты — на английском.

## Чего не делаем

Не делаем аккаунты, свой бэкенд, Firebase, аналитику и трекинг-SDK, рекламу, социальные функции, геймификацию, iOS и мультиплатформу. Не добавляй зависимости вне раздела «Стек», не спросив пользователя.

## Стек

- Kotlin, Jetpack Compose (Material 3), Navigation Compose, ViewModel + StateFlow, корутины.
- Gradle Kotlin DSL и version catalog (`gradle/libs.versions.toml`). Версии — последние стабильные на момент добавления. Проверяй их, не выдумывай.
- Модули: `:app` (Android) и `:domain` (чистый Kotlin/JVM без Android-зависимостей: расчётный движок, парсер, валидаторы, модели).
- Room с FTS4 для данных, `exportSchema = true`, только явные миграции, никакой destructive migration. DataStore — для настроек.
- OkHttp + kotlinx.serialization. Клиенты Claude API, Open Food Facts и USDA FDC пишем сами, тонкими. Официальный `anthropic-java` не берём: нам нужен один эндпоинт, полный контроль над tool loop и SSE и минимум зависимостей.
- CameraX + ML Kit Barcode Scanning (bundled-модель, распознавание на устройстве).
- Health Connect (`androidx.health.connect:connect-client`) — с фазы 2.
- Glance для виджета, WorkManager для фоновых задач.
- Графики: Vico или собственный Canvas. Выбери в фазе 2 и обоснуй.
- DI вручную через `AppContainer` в `Application`, без Hilt и Koin.
- `minSdk 28`, `targetSdk` — актуальный стабильный.

## Модель данных (Room)

- `Food`: id, name, brand?, aliases (через FTS), kcal, protein, fat, carbs, fiber?, basis (`RAW` | `COOKED` | `AS_SOLD`), source (`LABEL` | `OFF` | `USDA` | `WEB` | `CLAUDE_ESTIMATE` | `MANUAL` | `RECIPE`), sourceRef? (EAN, fdcId или URL), confidence? (`HIGH` | `MEDIUM` | `LOW`), barcode?, usageCount, lastUsedAt, archived, createdAt, updatedAt. Все нутриенты на 100 г (для напитков — на 100 мл, они приравниваются к граммам).
- `Portion`: foodId, name («шт», «ст. л.», «моя кружка»), grams.
- `Recipe` (id, name, cookedWeightG) и `RecipeItem` (recipeId, foodId, grams). Рецепт материализуется в `Food` с `source = RECIPE`: сумма нутриентов сырых ингредиентов делится на вес готового блюда.
- `MealTemplate` и `MealTemplateItem` — сохранённые приёмы пищи.
- `LogEntry`: id, date (LocalDate), time, foodId?, foodName, grams и **снапшот** kcal/protein/fat/carbs на момент записи, inputMethod (`TEXT` | `VOICE` | `BARCODE` | `LABEL` | `PHOTO` | `QUICK` | `TEMPLATE`), note?.
- `DayStatus`: date, incomplete (Boolean), note?.
- `WeightEntry`: date, kg, source (`MANUAL` | `HEALTH_CONNECT`). Одно значение на дату: ручное важнее импортированного.
- `ModelSnapshot`: date, trendWeight, tdeeRaw?, tdee, target, deficit, capped, proteinTarget, includedDays, weighIns. Пишется ежедневно, нужен для графиков и сглаживания.
- `AiCallLog`: ts, purpose (`PARSE` | `RESOLVE` | `LABEL` | `MEAL_PHOTO` | `ANALYSIS` | `CHAT`), model, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, webSearches, costUsd (по ценам из конфига), ok, errorCode?.
- `PendingItem`: нераспознанный ввод без сети, распознаётся позже (фаза 2).

## Доменные инварианты (нарушать нельзя)

1. Значения КБЖУ попадают в каталог только из этикетки (vision + подтверждение), OFF, USDA, веб-источника с URL, ручного ввода или помеченной оценки Claude. Поля `source` и, где применимо, `sourceRef` обязательны.
2. Ни одно число от LLM не сохраняется без экрана подтверждения, где пользователь видит источник и может поправить каждое поле.
3. Всю арифметику (граммы × нутриенты, суммы, TDEE, бюджет) делает код. LLM никогда не считает итоги.
4. Записи хранят снапшот нутриентов: правка продукта не меняет историю.
5. Валидатор энергии на каждом черновике продукта: `|kcal − (4·P + 4·C + 9·F + 2·fiber)| / kcal ≤ 15 %`, иначе показать предупреждение (не блокировать). Санити-проверки: kcal ≤ 900 на 100 г, P + F + C + fiber ≤ 100 г на 100 г, неотрицательные значения.
6. Без ключа API и без сети приложение полностью работает: ручной ввод, каталог, локальный парсер, расчёты. Сканер штрихкодов с OFF требует только сеть, не ключ. AI-функции — надстройка, их отсутствие не ломает потоки.
7. Цель по калориям никогда не опускается ниже BMR по формуле, дефицит не превышает 25 % расхода.

## Расчётный движок (`:domain`)

Все константы вынести в `EngineConfig`.

1. **Трендовый вес.** EMA с α = 0,1 по календарным дням. Дни без взвешивания переносят предыдущее значение тренда, старт — первое взвешивание.
2. **Наблюдаемый расход.** Окно W = 28 дней, заканчивается вчера.
   - `included` — дни окна с записями, не помеченные `incomplete`.
   - `weighIns` — взвешивания в окне.
   - Если `included ≥ 14`, `weighIns ≥ 8` и между первым и последним взвешиванием в окне ≥ 14 дней:
     `slope` = OLS-наклон веса по индексу дня (кг/день); `tdeeRaw = mean(intake по included) − slope × 7700`.
   - Иначе `tdeeRaw = null`.
3. **Априорная оценка.** Миффлин — Сан Жеор (трендовый вес, рост, возраст, пол) × коэффициент активности из настроек.
4. **Смешивание.** `w = min(1, included / 28)`, `blended = w·tdeeRaw + (1 − w)·prior`. Если `tdeeRaw == null`, то `blended = prior`.
5. **Сглаживание во времени.** `tdee_t = tdee_{t−1} + 0,2·(blended_t − tdee_{t−1})`. Хранится в `ModelSnapshot`, пересчёт раз в день и при изменении данных за прошлые дни.
6. **Цель.** `deficit = rate% / 100 × trendWeight × 7700 / 7`, ограничен 25 % от `tdee`; `target = max(tdee − deficit, BMR)`. Флаги `capped` и `bmrFloor` показываются в UI.
7. **Белок.** `proteinPerKg × trendWeight`.
8. **Недельный бюджет** (режим по умолчанию, неделя с понедельника):
   `allowance(day) = clamp((7·target − Σ c_i за прошлые дни недели) / оставшиеся дни включая сегодня, 0,75·target, 1,25·target)`, где `c_i` — фактический intake, если день включён, иначе `target`. Режим «дневной» даёт просто `target`.
9. **Предупреждения.** Темп выше 1 % массы в неделю; фактический темп за 4 недели быстрее цели более чем в 1,5 раза; белок ниже цели 5 дней из 7.

**Тесты движка обязательны.** Синтетика: истинный TDEE 2900, intake 2400 ± 150, шум веса SD 0,4 кг, 28 дней. В 95 % из 200 прогонов с разными сидами оценка `tdeeRaw` в пределах ±6 %. Плюс крайние случаи: нет взвешиваний, пропуски недель, все дни `incomplete`, смена цели посреди недели, переход через границу недели.

## Ввод и распознавание

### Быстрый путь, без сети
1. Детерминированный парсер в `:domain` разбирает строку на фрагменты по `,` (кроме десятичной запятой), `;`, переводу строки и `+`. Форматы: «название 230», «230 г название», «название 2 шт», «название 0,2 кг», «молоко 3,2% 200 мл». Единицы: г, гр, грамм, кг, мл, л, шт, ст. л., ч. л. Штуки и ложки переводятся в граммы через `Portion`; если порции нет, вес спрашивается у пользователя. Без единицы и при количестве ≤ 10, если у продукта есть порция «шт», это штуки.
2. Поиск в FTS по имени и синонимам: нормализация (нижний регистр, ё → е, без пунктуации), префиксные запросы. Ранжирование: точное совпадение, потом префикс, частота использования, давность.
3. Если каждый фрагмент однозначно сопоставлен и вес известен, запись делается сразу, с snackbar «Отменить».

### Путь через Claude
4. **PARSE** (быстрая модель). Нераспознанные фрагменты плюс для каждого топ-8 кандидатов из FTS → strict JSON: `[{fragment, foodId|null, grams|null, pieces|null, nameRu}]`. Весь каталог в промпт не отправлять.
5. **RESOLVE** (сильная модель, tool loop) для продуктов без `foodId`. Клиентские tools: `usda_search(query_en, data_types)`, `usda_food(fdc_id)`, `off_search(query, country="pl")`, `off_product(barcode)`. Серверный tool — web search Claude API, `max_uses` ≤ 3. Финальный ответ — strict tool `propose_foods` со схемой: nameRu, kcal, protein, fat, carbs, fiber, basis, source, sourceRef, confidence, typicalPortionName?, typicalPortionG?. Правила для модели: базы важнее собственных знаний; для USDA сначала перевести запрос на английский; собственная оценка допускается только как `CLAUDE_ESTIMATE` с confidence не выше `MEDIUM`.
6. Экран подтверждения (`ui/review`) показывает все позиции: сопоставленные (граммы редактируются) и новые (все поля редактируются, бейдж источника, результат валидатора энергии, флажок «сохранить в каталог»).

### Штрихкод
CameraX + ML Kit (EAN-13, EAN-8, UPC-A, UPC-E) → локальный каталог по `barcode` → `off_product`. Если у OFF есть нутриенты на 100 г, открывается подтверждение с `source = OFF`. Если нет — предложение сфотографировать таблицу пищевой ценности. Штрихкод сохраняется в продукте.

### Фото этикетки
**LABEL** (сильная модель, vision). Фото уменьшается до ~1568 px по длинной стороне, JPEG. Ответ — JSON через structured outputs: found, name, brand, kcal, protein, fat, carbs, fiber, per (`100g` | `100ml` | `serving`), servingG?, packageG?, ean?, notes. Пересчёт с порции на 100 г делает код, не модель. Дальше валидатор и подтверждение.

### Фото блюда (фаза 3)
**MEAL_PHOTO**: разложение на компоненты с оценкой граммов → каждый компонент через локальный каталог или RESOLVE → подтверждение. Всё помечено как оценка.

## Claude API

- `POST https://api.anthropic.com/v1/messages`, заголовки `x-api-key`, `anthropic-version`, `content-type`. **Перед реализацией сверь формы запросов с документацией (platform.claude.com/docs) и оставь ссылку в KDoc**: structured outputs (`output_config.format` для JSON, `strict: true` для tools), тип и версия серверного web search tool, `cache_control`, формат изображений, SSE-события, коды ошибок. Не пиши формы API по памяти.
- Модели задаются в `AiConfig` и меняются в настройках. По умолчанию: PARSE → `claude-haiku-5-5`; RESOLVE, LABEL, MEAL_PHOTO, ANALYSIS, CHAT → `claude-sonnet-5-5`. ID сверить со страницей моделей в документации.
- Prompt caching: `cache_control` на system prompt и определения tools, стабильные части промпта идут первыми.
- Retry: 429, 529 и 5xx — экспоненциальный backoff с учётом `retry-after`, максимум 3 попытки. Остальные 4xx не повторяются, показывается понятная ошибка.
- `AiCostTracker` пишет `usage` каждого ответа в `AiCallLog`. Цены за MTok лежат в конфиге с пометкой «сверить с pricing»; захардкоженных цен в логике нет. В настройках задаётся месячный лимит в $: при превышении AI-функции выключаются до конца месяца, с явным сообщением.
- Промпты хранятся в `ai/prompts/` как Kotlin-константы с версией (`PROMPT_RESOLVE_V3`). Версия пишется в `AiCallLog`.
- Таймауты: PARSE ≤ 15 с, остальное ≤ 90 с; у пользователя всегда есть кнопка «Остановить» (отмена корутины закрывает соединение).

## Внешние базы

- **Open Food Facts.** Ключ не нужен, но обязателен собственный `User-Agent` вида `Grammovka/<version> (<контакт>)`. Продукт: `/api/v2/product/{barcode}.json?fields=...`, только нужные поля. Нутриенты: `energy-kcal_100g`; если есть только `energy-kj_100g`, разделить на 4,184; `proteins_100g`, `fat_100g`, `carbohydrates_100g`, `fiber_100g`. Лимиты действуют на каждый эндпоинт, у поиска они особенно строгие: никакого поиска по мере набора, кэш ответов в Room на 30 дней, debounce. Актуальный поисковый эндпоинт и лимиты сверить с документацией OFF. Данные под ODbL: для личного использования ок, производную базу не публиковать.
- **USDA FoodData Central.** Ключ api.data.gov, вводится в настройках. `/fdc/v1/foods/search` с `dataType` Foundation и SR Legacy (для готовых блюд — Survey (FNDDS)), `/fdc/v1/food/{fdcId}`. Энергия: nutrient 1008 (kcal); у Foundation её может не быть, тогда 2047 или 2048 (Atwater). Белок 1003, жиры 1004, углеводы 1005, клетчатка 1079. ID сверить с документацией FDC. Запросы только на английском.

## Health Connect (фаза 2)

Чтение: вес (импорт в `WeightEntry`, если ручного значения за дату нет), шаги, тренировки (ExerciseSession). Тренировки используются только в аналитике и для опционального сдвига бюджета внутри недели (+N % в день тренировки длиннее X минут за счёт остальных дней, сумма за неделю не меняется). В расход не входят. Запись (фаза 3, по флагу): `NutritionRecord` по дням. Разрешения запрашивать по месту, при первом использовании функции.

## Безопасность

- API-ключи Anthropic и USDA вводятся в настройках и хранятся зашифрованными: AES-GCM ключ в Android Keystore, шифротекст в DataStore. EncryptedSharedPreferences не использовать, `security-crypto` объявлен устаревшим. Ключей нет ни в репозитории, ни в `BuildConfig`, ни в логах.
- Кнопка «Проверить ключ» делает минимальный запрос и показывает результат.
- Android Auto Backup включён для БД и настроек, хранилище секретов исключено из бэкапа (`dataExtractionRules` и `fullBackupContent`).
- Экспорт и импорт: полный JSON (каталог, записи, вес, настройки без секретов) и CSV (записи; итоги по дням с весом, трендом и целью) через Storage Access Framework.
- Сетевые логи в debug — без заголовков с ключами.

## UX-принципы

- Нижняя строка ввода доступна с экрана «Сегодня» всегда: текст, микрофон (фаза 2), сканер, камера этикетки.
- Экран «Сегодня»: остаток бюджета крупно, белок с прогресс-баром, жиры и углеводы мелко, список записей по времени, вес дня, переключатель «день записан не полностью».
- Чипы частых и недавних продуктов с последней граммовкой: повтор в один тап.
- У каждого продукта виден бейдж источника. Оценка Claude визуально отличается.
- Цифры моноширинные (tabular), без лишних знаков после запятой.
- Ошибки говорят, что случилось и что делать. Без извинений и без «что-то пошло не так».
- Тёмная и светлая тема, крупный тап-таргет, работа одной рукой.

## Фазы и критерии готовности

Перед началом каждой фазы покажи план-чеклист и дождись «ок». После фазы — короткий отчёт: что сделано, что отложено, известные проблемы.

**Фаза 0. Скелет.**
Gradle-проект, модули `:app` и `:domain`, version catalog, навигация с четырьмя вкладками (Сегодня, Каталог, Прогресс, Настройки), Room с первой схемой и экспортом, DataStore, `AppContainer`, `SecretStore`, экран ключей с проверкой, release-подпись (keystore вне репозитория, пароли из `local.properties` или переменных окружения).
Готово, когда: `gradlew.bat test` и `gradlew.bat :app:assembleRelease` проходят, APK ставится, ключ сохраняется, проверяется и переживает перезапуск.

**Фаза 1. MVP.**
Каталог (CRUD, FTS, порции, синонимы, архив). Экран «Сегодня». Детерминированный парсер и локальная запись с отменой. Вес. Движок с тестами. Штрихкод + OFF. Фото этикетки. PARSE и RESOLVE с USDA, OFF и web search. Экран подтверждения. Частые продукты. Флаг неполного дня. Экспорт и импорт. Auto Backup. `AiCallLog` и месячный лимит.
Готово, когда проходят сценарии:
1. «азиатская груша 230» в первый раз → RESOLVE находит USDA → подтверждение → запись. Во второй раз в авиарежиме запись мгновенная.
2. «творог 5% 150, кофе с молоком» → один продукт из каталога, второй через RESOLVE.
3. Штрихкод польского продукта → OFF → подтверждение. Повторный скан находит продукт локально.
4. Фото таблицы на польском → черновик, валидатор энергии зелёный.
5. Без ключа: ручное добавление и запись работают, AI-кнопки скрыты или объясняют, что нужен ключ.
6. Тесты движка и парсера зелёные (таблица из 40+ русских вводов).

**Фаза 2. Ежедневное удобство.**
Health Connect (вес, шаги, тренировки). Glance-виджет (остаток, белок, кнопки «добавить» и «сканер»). Голосовой ввод (SpeechRecognizer, ru-RU) в тот же парсер. Рецепты с весом готового блюда. Шаблоны приёмов пищи и «повторить вчерашний завтрак». Напоминания: утреннее взвешивание; утром вопрос «вчера всё записано?» с действиями «да» и «нет — неполный». Офлайн-очередь `PendingItem`. Графики: вес и тренд, расход по `ModelSnapshot`, intake против цели, недельная таблица.

**Фаза 3. Аналитика.**
Фото блюда. Еженедельный разбор (WorkManager в воскресенье вечером → уведомление → экран со стримингом ответа). Агрегаты за 4 недели готовит код, модель получает только их. «Спроси дневник» — чат с read-only tools над локальной БД: `get_day_summaries(from, to)`, `get_entries(from, to)`, `get_top_foods(from, to, by)`, `get_model_state()`, `get_weights(from, to)`; ответы модели не меняют данные. Запись `NutritionRecord` в Health Connect. Сдвиг бюджета в дни тренировок.

## Правила работы

- Маленькие шаги: изменение → `gradlew.bat test` → сборка → коммит с осмысленным сообщением. Не накапливай большие несобранные диффы.
- Не угадывай API: Android, Health Connect, ML Kit, Claude API, OFF, USDA — сверяй с официальной документацией и оставляй ссылку в KDoc у клиента или адаптера.
- Сетевые клиенты закрыты интерфейсами. В тестах — фейки и записанные фикстуры JSON в `src/test/resources`, реальных вызовов API в тестах нет.
- Миграции Room — с тестом миграции.
- Если требование неоднозначно или решение меняет модель данных, спроси, а не выбирай молча.
- Секреты не печатай в выводе, логах и коммитах. `.gitignore` с первого коммита: `local.properties`, keystore, `*.jks`, `/build`, `.idea` (кроме общих настроек).
- Обновляй раздел «Состояние» внизу этого файла после каждой фазы.

## Окружение и команды

- Разработка на Windows: JDK 17+, Android SDK (command-line tools или Android Studio), `adb` в PATH. Перед фазой 0 проверь, что всё доступно, и скажи, чего не хватает.
- Сборка: `gradlew.bat :app:assembleDebug`, тесты: `gradlew.bat test`, линт: `gradlew.bat lint`.
- Установка на телефон: `adb install -r app\build\outputs\apk\debug\app-debug.apk` (USB или беспроводная отладка `adb pair`/`adb connect`).
